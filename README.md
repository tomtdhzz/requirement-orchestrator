# Requirement Orchestrator（需求编排器）

**中文** · [English](README.en.md)

**任何工作方式之上的委派与验收控制层。** 有 SDD 框架就用它的 spec，没有就现场立一个最小可验收的规格；它只管两件事——**扇出前必须先冻结什么**，以及**凭什么算做完**。

给一个人用。一个人同时驱动多个 agent 时，瓶颈不是产能而是**验收**。

## 它拦住的是这种事

> 你派了两个 agent 改同一个 Go package 里**不同的文件**。写范围不重叠，看起来完全可以并行。
> 结果两边的 `go test` 都在红——因为对方半写的文件正在参与编译。你花了半小时才意识到问题不在自己的代码里。

> 另一个 agent 回来说"改完了，测试通过"。你信了。三天后发现那个改动根本不在 diff 里——它跑的是改动之前就存在的绿灯。

这两件事的共同点：**失败发生时你没有判据，只有印象。** 这个 skill 提供的就是判据：

- 能不能并行，判的是**是否共享同一个编译/测试目标**——不是"改的文件是否不同"。后者是最常见的错误答案，上面第一个故事就是它造成的。
- 算不算做完，判的是 **`base_commit..HEAD` 的实际 diff**——不是 worker 的报告。第二个故事就是信报告的代价。

## 30 秒上手

```bash
npx skills add tomtdhzz/requirement-orchestrator -g -y
```

然后对你的 agent 说一句（不需要先有 spec、不需要改造仓库）：

> 用 requirement-orchestrator 分析这个需求：给订单接口加个限流。

**你会看到它先产出规格与验收场景、再给出任务切分与并行判定，然后停下来等你确认**——`analyze` 是只读的，改代码需要你另外授权。这一停是设计，不是卡住。

## 和别的东西有什么不一样

| 你会问 | superpowers 这类 skill 集 | 宿主自带的 orchestrator 模式 | 本 skill |
|---|---|---|---|
| 开始前要先有什么？ | 装一套 skills，先 brainstorm 出计划文档 | 无（也没有规格与验收概念） | **无**——不改造仓库，不要求 spec |
| 谁说了算"做完了"？ | 证据先于声明，但由做事的一方自评 | 模型自述 | **控制方读 diff 判定；worker 只能报 `review`** |
| 两个任务能不能同时跑？ | 启发式：不同测试文件 / 子系统 | 不判定 | **判据：是否共享编译/测试目标；且必须留下扫描表** |
| 换个宿主还在吗？ | 偏 Claude 生态 | 绑定该宿主 | **纯 Markdown，Codex / Claude 换着用原样生效** |

同层的 spec / 任务框架（spec-kit、OpenSpec、BMAD、ccpm、task-master）每一家都要求一个**前置产物**才能开始：一份 spec、一个现状层、`uv` + 渲染器、一个 GitHub issue、一个 API key。本 skill 要求的是零。**"轻量"是形容词，"零前置"是可核对的事实。**

至于宿主（Claude Code / Codex / omp）：它们提供的是"能不能做到"，不是"什么算做完"。带编排模式的宿主给的是**路由**不是**门**。而宿主能做本 skill 做不到的**阻止**（hooks / CI）——所以两者是叠加：**能力会被宿主吸收，判据不会。**

## 什么时候别用它

- **一次性小改、你自己动手就完了**——它的价值在委派与验收，没有委派时大部分机制退化。
- **你要的是任务看板、进度同步、团队协作**——那是明确的非目标，去用 ccpm 或你们的工单系统。
- **你要的是"帮我把 spec 写出来"**——那是 spec-kit / OpenSpec 的活；本 skill 只在没有 spec 时立一个够验收用的最小规格。
- **你希望它能阻止 agent 干坏事**——它做不到。它让违反**可被发现**，真正的阻止要在宿主侧加钩子。

## 它实际产出什么

一句口头需求进去，出来的不是计划散文，而是四样可核对的东西：

1. **薄到能验收的规格** —— 一条需求 + 一个验收场景 + 冻结的契约（仓库已有 spec 就用现成的，绝不造第二份）
2. **并行判定与它的扫描表** —— 一行一对共享文件/编译目标/接口的任务；`"扫描是干净的"` 而没有这些行，不算做过扫描
3. **能被复跑的验证步骤**（派发契约里写命令，不写意图）

   ```yaml
   verification:
     - run: "npx jest test/api.rateLimit.int.spec.ts"
       expect: "PASS — 429 body + Retry-After header present"
   ```

4. **按 diff 判定的完成** —— worker 说"做完了"不作数；控制方读 `base_commit..HEAD`、复跑上面的命令、核对写范围没越界，然后才记 `completed`

## 自证：我们用它开发它自己

本仓库这一轮的全部 51 个提交都走了这套流程（现场立规格 → 派发只读审计 → 按 diff 判定 → 记账）。它抓出来的问题，就是它自己的：

- **7 例"规则写了但在生效时刻读不到"**——其中 2 例是规则落地当天就不可达（新加的确认闸位于一个不会被加载的文件里）。这类缺陷只有系统性的可达性核查才能发现。
- **4 例"编辑回执说成功、内容不对"**——包括一次静默删掉了清单里的一行。全部由独立复核 diff 抓到，而不是由编辑工具的成功回执。
- **7 项候选功能被判定为"不该由这个项目持有"**——它们代价低、频率高、也写得完，只是属于 spec 生产或任务调度的领域。

这些数字不是营销，是本仓 `CHANGELOG.md` 与 git 历史里可以逐条核对的东西。

## 三根支柱

- **零前置** —— 不要求 spec、不要求安装、不要求任务库或账号。
- **输入形态无关** —— 功能、变更、缺陷、"帮我看看这段代码"走同一个控制环。缺陷只是其中一类输入，特殊之处仅在于多一步"先复现再断根因"。
- **控制权与证据分离** —— worker 只能提交 `review`，唯有控制 agent 凭证据判 `completed`。

## 路线图

**在做**

- **临时方案的回收机制**。缺陷侧的止血、需求侧的 hardcode、评审侧被 defer 的 finding——现在它们都容易被包装成正式方案混过验收，而一旦记成 `completed` 就永远不会被回收。判据是：临时方案必须是**有意识的、被记录的、带回收条件的**。
- **worker 回报契约细化**：`review` 之外区分"做完但存疑"与"缺上下文"，让控制方能按状态选动作而不是逐字读报告。

**接下来**

- **`Freeze Before Fanout`（冻结先于扇出）概念文档**，中英各一份。三个冻结——契约、范围（以编译/测试目标为界）、事实与其出处——是这个项目里唯一还没被别人命名的东西。
- **组合验证**：在一个真实装有 spec-kit / OpenSpec 的仓库里完整跑一遍，把"用它们的 spec、用我们的门"落成可复述的记录。
- **把无法产生证据的规则下沉到宿主**：提供可选的 hooks 样例（编辑后回显 diff、提交前拦混 concern），而不是在 skill 里内置运行时。

**永远不做**

云端后端与账号 · 任务库 / 看板 / 仪表盘 · 生成 spec 本身 · 任务排序调度算法 · 绑定单一宿主的运行时。这些不是"还没做"，是判定为不该由这个项目持有——理由随每一条记录在案。

## 深入

规范在 [`SKILL.md`](SKILL.md)（90 行，常驻上下文），细节在 [`references/`](references)（15 篇，按需加载，共约 950 行）。二者与本 README 冲突时以 `SKILL.md` 为准。

- 塑造规格与冻结契约 → `spec-driven.md`；分解前接地 → `context-grounding.md`
- 分解、并行门、重规划 → `decomposition.md`；验收证据、根因路由、复评收敛 → `verification.md`
- 子 agent 契约 → `agent-contract.md`；账本与断线续跑 → `ledger.md`；批量与单行改动的回读 → `mutation.md`
- 压力测试既有需求/设计/实现 → `challenge.md`；平台差异 → `*-adapter.md`

## 环境与依赖

- 纯**方法论 skill（只有 Markdown）**：无运行时、无 `pip`/`npm` 依赖、不装任何包。
- 需要一个能读 `SKILL.md` 的 **agent 宿主**：Claude Code（omp）、Codex，或任何你让它读 `SKILL.md` 的 agent。
- 可选集成：[skills-radar](https://github.com/tomtdhzz/skills-radar) 作为起点能力库（见 `references/knowledge-base.md`）。

## 限制与非目标

- **没有强制力。** 纯 prompt 制品：规则给出的是**可观察的检查点，不是阻止**。它让违反在事后被抓到，不能让违反不发生。真正的强制要在工具侧（编辑后回显 diff、pre-commit 钩子、CI 门）。
- 因此 [`references/verification.md`](references/verification.md) 的证据标准是整套东西里唯一把"自觉"变成"可检验"的部分。删掉它，其余规则就只剩措辞。
- **常驻成本是真实的。** `SKILL.md` 每次会话都进上下文；这就是为什么每条规则都必须带撤回条件（见 [CONTRIBUTING.md](CONTRIBUTING.md) 的 `Retiring a rule`）。
- **并行门是判据，不是锁。** 它告诉你能否同时跑，不做隔离；工作树隔离取决于你自己的 git 习惯。
- **ledger 是文件，不是数据库。** 跨会话续跑靠它，但它被改坏或过期时没有仲裁者——恢复时必须把 `in_progress` 当未验证重新核对。
- **非目标**：不做任务库、看板或仪表盘；不托管任何状态；不生成 spec 本身；不提供跨平台的强一致状态。
