# Freeze Before Fanout：冻结先于扇出

## 主张

没有冻结的边界，就没有并行。

今天的 agent 编排翻车，几乎都不是模型能力不够，而是**扇出太早**：在契约、范围、事实这三样东西还没定住的时候，就把工作分给了两个以上的执行者。之后发生的一切都是这一步的后果——两个写入者改同一个编译目标，各自本地"通过"，合起来编不过；两份实现各按自己猜的接口写，集成期成片返工；一个执行者把另一个执行者的推测当成事实继续推导，结论漂到无人能溯源。

冻结不是流程仪式，它是并行的**前置条件**：三样东西定住之后，并行才是安全的；定不住的时候，正确的动作是不并行。

三个冻结分别是 **Contract**（契约）、**Scope**（范围）、**Fact**（事实与出处）。下文给出每一个的失败后果与可观察判据。

## 无人命名的那一步

现有框架都在优化这条链上的某一端。

- 前端：**spec 写得好不好**。spec-kit（133k★）、OpenSpec 这类工具把需求、验收、契约结构化，解决"输入含糊"。
- 后端：**完成说得实不实**。`obra/superpowers`（281k★）的 `verification-before-completion` 解决"执行者自称做完了"。

中间这一步——**从一份已经写好的 spec，到把工作真正切开派出去之前，必须先定住什么**——没有任何一家把它命名。片段实现到处都有：BMAD 有角色边界，superpowers 有验证门，spec-kit 有契约产出。片段各自都被验证过，但没有一家把它们组装成一件可教的事，于是也没有人能在扇出前照着它逐条检查。

为什么中间这一步最贵：编排的代价落在三处——常驻上下文（每次会话都付）、agent 往返（每个任务都付）、人的注意力（每道门都付）。spec 写得再好，扇出错了就要重派任务、重跑往返、重占人的注意力，三处同时付第二遍。这是整条链上唯一一处"做错要全额重付"的位置。

这份文档不发明新概念。它给一件已经在做、却一直没有名字的事一个名字，并给出它的失败判据。

## 三个冻结

扇出前必须定住三样东西。每一样有自己的失败形态，也有自己的观察方法。

| 冻结对象 | 不冻结的后果 | 可观察的判据 | 本仓落点 |
| --- | --- | --- | --- |
| **Contract** 契约 | 集成期冲突、成片返工 | 契约文本是否已存在，且在依赖它的任务完成前不可变更 | [../references/spec-driven.md](../references/spec-driven.md) |
| **Scope** 范围 | 静默覆盖、构建与测试互毁 | 两个任务是否落在**不同的编译/测试目标**上（不同文件不算） | [../references/decomposition.md](../references/decomposition.md) |
| **Fact** 事实与出处 | 幻觉派生、结论漂移 | 每个派生值（分类、判断、风险评级、建议）能否指回一条已核实事实 | [../references/verification.md](../references/verification.md) |

三条判据都能当场检查：契约文本存在或不存在；两个写入范围的编译目标相同或不同；一个结论能或不能指回一条事实。没有一条依赖"是否充分""是否清晰"这类形容词——这是刻意的，形容词判据无法被观察到不成立。

Contract 与 Scope 只在有委派时才需要冻结；Fact 与是否委派无关（见"什么时候不需要它"）。

三种最常见的假冻结，形式上都像已经冻过了：

- 契约只存在于对话里，没有落成文本——下一个会话看不到它，等于没冻。
- 范围按文件划分而不按编译/测试目标划分——同一个包里的两个文件不是两个范围。
- 事实来自另一个执行者的摘要，而不是一次实际的读取或运行——摘要可以是推测的转述。

## 控制平面：Freeze → Fanout → Fan-in

三段各有一件不能省的事。

**Freeze.** 三个冻结全部落地。在存量代码库里还要多一步：把未知分阶段重新接地——先确认仓库与分支状态、构建基线，再确认代码事实，最后才谈契约。跳过接地的冻结，冻住的是猜测。

**Fanout.** 一个控制 agent 独占派发权，执行者之间不互相派工。只派发契约完整的任务：目标、写入范围、验收判据、依赖，缺一不派。要写本地工作树之外的系统（wiki、工单系统、数据库、远程 API）时先做 preflight——权限与其精确范围、限流与失败是否静默、结果能否读回，在派发前查清，而不是在批量执行中途发现。

**Fan-in.** 证据门验收：执行者只能提交待审，只有控制方能判完成；批量改动靠独立回读和结构差异确认，不采信工具自报的成功数。

三段之间**控制权不转移**：派发权、验收权、重规划权全在同一个控制方手上。任何一段把判断下放给执行者，另外两段的记录就对不上——没人能说清谁清过哪条边界。

**这一段不主张原创。** 它是对已有实践的复用：`obra/superpowers` 的 `verification-before-completion` 以 281k★ 占住了这个位置，其铁律是 `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`。本文档在这里明确复用而非重新发明——Freeze Before Fanout 主张的是**扇出之前**那一步，不是验收标准本身。

## 一次真实运行

2026-09-01，Claude Code，一个 Go 项目的分支部署失败排查。以下细节全部来自那次运行的手记。

**Fact 冻结生效。** CI 的构建阶段报了三条 `undefined`。三条错误、三个符号，最顺手的动作就是拆成三个 bug、三个子任务并行修。挡住这个动作的是根因判据：本仓的拆分轴写的是"bug 根因与修复路径"，是**根因**不是**症状**，于是必须先回答"这三条是不是同一个原因"。答案是同一个——分支落后 master 两个提交，而分支上另一个提交又照着 master 的代码形态重写了那个文件，引用了本分支根本不存在的符号。三个症状，一个根因，一个任务。

没有这条判据会怎样：三个任务并行改同一个包，各自"修好"自己那条报错，谁都碰不到真正的原因，报错换个符号继续出现。

**Contract 冻结生效。** 在动手解冲突**之前**，识别出 `prometheus.MustRegister` 的进程级全局注册约束：两侧同名指标去重不彻底，进程会在启动时 panic。**这不是编译器能报出来的问题**——编译干净，故障发生在启动那一刻。它是靠"识别共享状态约束"这个主动动作查出来的，对应契约冻结清单里"进程级全局注册"那一条。

没有这条会怎样：冲突解完、构建通过、上线 panic，而且现场看不出与那次合并有关。

**诚实标注：那次运行全程没有派发任何子 agent**，控制方就是单个会话。所以这个案例验证的是**判据本身**——根因判据挡住了错误的切分，共享状态判据抓到了编译器抓不到的冲突——而不是并行执行的收益。同一份手记里也记着代价：判据不是免费的，有一条要求"每种模式都读参考文档"的规则，在那个三行编译错误的任务上被自然绕过了，因为读两份文档的开销与任务不成比例。

## 什么时候不需要它

单任务、单会话、无委派时，Contract 与 Scope 冻结退化为自问自答：没有第二个写入者，就没有要保护的边界，写一份只有自己看的"冻结契约"是纯开销。

仍然值得做的只有 Fact 冻结。"派生结论指不回事实"这件事与有没有并行无关——上一节那次运行就是单会话，它的两个收益都来自判据，不来自并行。

判断方法很粗但够用：写入者 ≤ 1 时只做 Fact 冻结；写入者 ≥ 2 时三个冻结全做，缺一不扇出。把三个冻结当成无条件仪式，会在小任务上被绕过——三行编译错误撑不起一套契约文档，硬套的结果是规则整体失去可信度。

## 可测判据

这个概念自带失败判据。如果 Freeze Before Fanout 是空话，你会观察到它不成立；反过来说，下面任一症状出现，就是某个冻结没做。

1. **并行写入者互毁。** 两个执行者各自报告"本地通过"，合起来编不过或测不过。→ Scope 没冻结：两个写入范围落在同一个编译/测试目标上。
2. **集成期成片返工。** 任务级验收全绿，集成时接口、字段名或错误形态对不上，返工量与已完成量同阶。→ Contract 没冻结：契约是在实现中途被发现的，不是在扇出前被写下的。
3. **派生结论指不回事实。** 某个分类、风险评级或建议追不到一条已核实来源，或者追到的是另一个执行者的推测。→ Fact 没冻结。

三条都能在事后从产物里查证，不需要相信任何人对过程的叙述。这既是判断这份文档有没有用的方式，也是判断你这次扇出做对了没有的方式。
